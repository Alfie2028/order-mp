## 一、共性基础题：优先掌握

### 01. 你的项目做了什么，解决什么问题？

参考回答：这是一个校园多档口点餐应用。学生可以选择餐厅，按档口浏览餐品，选择份量和加料，再经过购物车、结算和订单查询完成一次点餐流程。项目主要解决多个档口信息分散、选餐和订单信息不统一的问题。当前实现的是移动端本地交互原型。

追问“为什么做这个题目”：校园就餐场景容易理解，也能集中练习列表、表单、页面跳转、状态共享和本地存储等课程知识。不要声称已经实际减少排队时间；当前没有真实运营数据。

### 02. 为什么同时使用 uni-app 和 Vue？两者什么关系？

参考回答：Vue 提供响应式、组件化和模板机制；uni-app 基于 Vue 的开发方式提供跨端组件、页面配置和统一 API。项目用 Vue 写页面与业务逻辑，再由 uni-app 工具链构建 H5 或微信小程序。它们在这里承担不同层面的职责，并不冲突。

项目例子：`ref`、`computed` 来自 Vue；`onLoad` 来自 uni-app；页面跳转调用 `uni.navigateTo`。

### 03. uni-app 与普通网页、原生 App 有什么区别？

参考回答：普通网页主要面向浏览器；原生 App 通常直接使用目标平台的开发体系；uni-app 可以复用较多代码面向多个运行端。但各端组件、权限和运行环境存在差异，所以仍需适配和分别测试。

项目例子：点餐业务逻辑可以共享，地图在 H5 与非 H5 分别实现。当前展示 H5，已有小程序构建检查；没有完成 Android、iOS 安装包与所有端真机验证。

### 04. 什么是 MVVM？在你的项目中怎么体现？

参考回答：MVVM 可以从数据、视图和连接两者的视图模型来理解。页面读取响应式数据进行展示，用户操作通过事件修改数据，框架再更新视图。项目中购物车数组是数据，餐品列表和合计是视图，响应式状态与计算属性负责连接它们。

注意：不要把 MVVM 直接等同于“所有数据都双向绑定”。例如商品卡片接收的 props 仍然遵循单向数据流。

### 05. 项目目录怎么划分？几个核心文件分别做什么？

参考回答：`pages` 放业务页面，`component` 放公共组件，`data/catalog.js` 放目录数据，`store/app.js` 集中管理共享状态与操作，`utils` 放金额和时间格式化，`static` 放图片，`styles` 放公共样式。

入口上，`main.js` 创建应用，`App.vue` 承载应用级生命周期和全局样式，`pages.json` 注册页面与 tabBar，`manifest.json` 保存应用及平台相关配置。拆分后同类逻辑更容易查找和复用。

### 06. Vue 单文件组件和 `<script setup>` 是什么？

参考回答：一个 `.vue` 文件通常由模板、脚本和样式组成。`<script setup>` 是组合式 API 在单文件组件中的编译期语法糖，顶层变量、函数和导入可在模板中直接使用。项目把搜索条件、购物车展示和点击处理围绕功能组织在一起。

追问：`defineProps` 和 `defineEmits` 是编译宏，不需要从 Vue 导入。它们分别声明组件输入和组件事件。见 [Vue 响应式基础](https://cn.vuejs.org/guide/essentials/reactivity-fundamentals)。

### 07. `ref` 和 `reactive` 有什么区别？

参考回答：`ref` 可以包装基本类型或对象，在脚本里通常通过 `.value` 访问；`reactive` 为对象创建响应式代理，直接访问属性。项目用 `ref` 保存搜索词、数量和弹窗状态，用 `reactive` 保存规格选择对象与全局状态。

追问：`ref` 也能保存对象，不能说它只能保存基本类型。模板里的顶层 ref 通常自动解包，普通对象中嵌套 ref 不能一概按相同规则处理。见 [Vue 响应式基础](https://cn.vuejs.org/guide/essentials/reactivity-fundamentals)。

### 08. `computed`、`watch` 和普通方法有什么区别？

参考回答：`computed` 适合从已有状态推导值，并根据响应式依赖缓存；`watch` 适合数据变化后执行请求等副作用；普通方法在被调用时执行。购物车总价依赖餐品单价和数量，因此项目用 `computed` 计算。

追问“本项目用 watch 自动保存吗”：没有。当前是在加购、改数量和下单等操作后显式调用 `persist()`。不要把可行方案说成已经使用。见 [Vue 计算属性](https://cn.vuejs.org/guide/essentials/computed) 与 [Vue 侦听器](https://cn.vuejs.org/guide/essentials/watchers)。

### 09. `v-model` 是什么？项目哪里用了？

参考回答：它把表单控件的值与状态关联起来，输入会更新状态，状态变化也会体现在控件上。点餐页用 `v-model="keyword"` 绑定搜索词，结算页用它绑定备注。搜索结果再由计算属性根据关键词过滤。

追问：这不意味着所有组件间都应该直接修改对方数据。普通父子组件通信仍通过 props 和事件组织。

### 10. `v-if` 与 `v-show` 有什么区别？

参考回答：`v-if` 决定条件分支是否创建和保留；`v-show` 保留内容，通过显示样式控制可见性。频繁切换时可考虑 `v-show`，按条件出现且切换不频繁的内容可用 `v-if`。项目中购物车非空才显示底部购物车条，无搜索结果则显示空状态。

项目的购物车抽屉本体使用 class 和位移控制显示，以支持动画；不要把它说成使用 `v-show`。见 [Vue 条件渲染](https://cn.vuejs.org/guide/essentials/conditional)。

### 11. `v-for` 为什么要加 `key`？能用数组下标吗？

参考回答：稳定的 key 帮助框架识别列表中每一项，在增删和重排时保持正确的组件身份。商品列表使用 `product.id`，购物车使用组合后的 `item.key`。可能变化的列表使用下标容易导致状态与条目错配。

例子：删除第一条购物车记录后，第二条不应继承第一条组件的内部状态。见 [Vue 列表渲染](https://cn.vuejs.org/guide/essentials/list)。

### 12. 父子组件怎么通信？你封装了哪些组件？

参考回答：父组件通过 props 传入数据，子组件通过 emit 通知父组件处理操作。`ProductCard` 接收 `product`，点击卡片发送 `open`，点击加号发送 `add`；父页面决定打开详情还是直接加购。`EmptyState` 统一空内容提示与操作入口。

追问“为什么加号用了 `.stop`”：防止事件冒泡导致加购同时触发整张卡片的点击事件。见 [Vue 组件事件](https://cn.vuejs.org/guide/components/events)。

### 13. uni-app 常用生命周期有哪些？`onLoad` 与 `onShow` 有什么区别？

参考回答：`onLoad` 在页面加载时执行，可接收路由参数；`onShow` 在页面显示时执行，返回页面时可能再次触发；`onReady` 对应页面初次渲染完成；`onUnload` 对应页面卸载。应用启动可用 `onLaunch`。

项目例子：详情页通过 `onLoad` 读取餐品 id，结算页通过 `onShow` 检查购物车是否为空。页生命周期与 Vue 组件生命周期不要混为一谈。见 [uni-app 页面生命周期](https://uniapp.dcloud.net.cn/tutorial/page.html)。

### 14. 页面如何跳转和传参？

参考回答：`navigateTo` 保留当前页并进入非 tabBar 页；`redirectTo` 关闭当前页再进入非 tabBar 页；`switchTab` 切换配置的 tabBar 页；`navigateBack` 返回。项目打开详情用 `navigateTo`，下单后用 `redirectTo` 进入订单详情，进入点单主入口用 `switchTab`。

详情地址携带 `?id=...`，目标页通过 `onLoad` 读取。不要用普通详情页的传参方式解释 `switchTab`；首页选择档口时先更新共享状态，再切换 tab。见 [uni-app 路由 API](https://uniapp.dcloud.net.cn/api/router.html)。

### 15. 多个页面怎么共享购物车？用了 Vuex 或 Pinia 吗？

参考回答：没有。项目在模块作用域创建一个 `reactive` 状态，各页面调用 `useAppStore()` 得到同一个状态及其操作方法。`cartCount` 和 `cartSubtotal` 由计算属性推导，避免每个页面各算一份状态。

追问“为什么不用 Pinia”：当前规模较小，使用集中状态模块就能表达业务；模块和多人协作扩大后可考虑 Pinia。不能仅因为函数叫 `useAppStore` 就说它是 Pinia。

### 16. 手机屏幕大小不同，如何适配？`rpx` 是什么？

参考回答：rpx 是 uni-app 的响应式尺寸单位，按 750rpx 设计基准理解移动端布局；项目同时使用 Flex、百分比和安全区间距，使内容随屏幕变化。桌面 H5 还通过媒体查询限制内容宽度。

例子：固定在底部的操作条加入 `env(safe-area-inset-bottom)`，减少与底部手势区重叠。rpx 不是任何设备上都等于 1px；布局仍要检查长文本、小屏幕和不同平台。见 [uni-app 页面样式与布局](https://uniapp.dcloud.net.cn/tutorial/syntax-css.html)。

### 17. 什么是条件编译？与 `v-if` 有什么区别？

参考回答：条件编译在构建时按目标平台保留对应代码；`v-if` 在运行时按数据决定内容是否渲染。项目地图在 `#ifdef H5` 中使用 iframe，在 `#ifndef H5` 中使用 map 组件，以处理平台差异。

追问：多端复用不代表所有平台不经测试即可运行。项目实际检查过哪些端，应分别说明。见 [uni-app 条件编译](https://uniapp.dcloud.net.cn/tutorial/platform.html)。

### 18. 数据保存在哪里？刷新为什么还在？与数据库有什么区别？

参考回答：商品目录在本地 JS 文件中，运行状态通过 `uni.setStorageSync` 写入缓存，初始化用 `uni.getStorageSync` 读取。当前键是 `CAMPUS_ORDERING_V11`。因此同一站点、同一浏览器环境下刷新可恢复。

本地缓存不等于服务器数据库，无法实现多用户共享、可靠权限与事务控制。`localhost` 和 `127.0.0.1` 是不同站点来源，切换地址可能看到不同数据；清理缓存也会丢失本地状态。同步 API 对少量数据方便，大数据频繁写入应评估阻塞与异常处理。见 [uni-app 数据缓存](https://uniapp.dcloud.net.cn/api/storage/storage.html)。

### 19. 如何请求后端数据？异步如何处理？

参考回答：当前点餐主流程直接读取本地目录，没有调用业务后端。若接入服务端，可以用 `uni.request` 封装请求层，统一处理接口地址、登录信息、超时和错误，再用 Promise 或 async/await 组织调用。请求期间展示加载状态，失败时允许重试。

追问“异步是什么意思”：请求结果不会立刻返回，后续依赖结果的步骤要等请求完成；async/await 便于表达这种先后关系，不表示请求变成同步阻塞网络调用。当前支付里的 `setTimeout` 仅模拟等待，不能当作后端接口实现。

### 20. 你怎么测试项目？出了问题怎么排查？

参考回答：先检查构建，再按用户路径验证选餐、规格、数量、优惠和订单；还要检查空购物车、无搜索结果、刷新恢复、切换餐厅等边界。出错时先看控制台和具体复现步骤，再沿着页面事件、状态方法、数据和存储逐层定位。

项目已有 H5 交互与双端构建的历史记录；没有完整自动化测试体系，也不能把构建成功当作真机功能全部正常。本次文档提供的是可重复演示与待执行测试清单，不冒充新完成的测试报告。

## 二、项目实现题：能打开代码说明

### 21. 餐厅、档口和餐品之间怎么关联？

参考回答：餐厅列表来自 `STORES`，档口来自 `STALLS`，餐品来自 `PRODUCTS`。餐品通过 `stallId` 关联档口，订单保存当前餐厅的 `storeId`。当前实现共用一套档口和菜单，切换餐厅主要改变当前门店信息与订单归属。

追问“这算真实多商户吗”：目前是多档口选餐演示，没有独立商户后台、独立库存、档口子订单和分别结算。扩展时需要让档口关联餐厅，让商品关联真实档口，并设计订单拆分。

### 22. 购物车为什么有的餐品合并，有的分开？

参考回答：购物车用商品 id 与排序后的已选规格 id 生成组合键。相同键增加数量，不同键创建新条目。这样同一道餐品选不同份量或加料时可以分别保存。

较深追问：目前只拼接选项 id，没有包含规格组 id。现有“标准份”和“标准辣”等选项存在相同 id，未来更复杂组合可能碰撞；改进应使用 `groupId:optionId` 的规范化组合。不要宣称当前键设计在任何扩展下都绝对唯一。

### 23. 不同餐品规格差别很大，如何复用详情页？

参考回答：把规格设计成数据。每组包含 id、名称、是否多选及选项列表，选项记录附加价。详情页遍历规格组，单选保存一个 id，多选保存 id 数组，再汇总已选项计算价格。

例子：水饺可配置个数与蘸料，饮品可配置杯型和甜度，不需要各写一个详情页。当前单选会初始化第一个选项；数据中的 `required` 字段还没有形成通用必选校验，不能把它说成已实现完整校验引擎。

### 24. 价格怎么计算？为什么用“分”？

参考回答：餐品单价等于基础价加规格附加价，小计等于单价乘数量，购物车总额为各条目之和，实付再减符合条件的优惠。存储和计算以整数“分”为单位，展示时除以 100，减少小数浮点运算造成的金额误差。

例子：黑椒鸡腿饭 1880 分，加蛋 200 分，得到 2080 分。`toFixed(2)` 用于展示两位小数，它不是金额精度问题的全部解决方案。

### 25. 优惠券是怎么使用的？

参考回答：结算页根据用户持有的券 id 和当前金额门槛筛选可用券；创建订单时再检查门槛，计算减免金额，使用后从本地券列表移除。实付金额下限为 0，避免出现负数。

追问边界：目前没有校验到期日，创建订单的方法也没有完整复核持有状态；如果选券后购物车金额变化，预览优惠还需重新校验。真实服务端必须统一校验资格、门槛、有效期与是否已核销。

### 26. 点击确认支付后发生什么？如何防止重复提交？

参考回答：先检查购物车是否为空和是否正在提交，然后设置 `paying` 并显示加载提示。延时后调用 `createOrder` 创建本地订单，清空购物车，关闭加载，再跳转订单详情。`paying` 避免这一页面在提交中重复处理点击。

当前没有调用真实支付，支付方式也没有保存到订单。前端防连点不等于服务端幂等；真实系统仍需唯一请求标识、订单状态校验和可靠支付回调。

### 27. 为什么订单要复制购物车？“再来一单”怎么实现？

参考回答：订单应记录下单时的商品名、规格、价格和数量。如果只保存购物车对象引用，后续修改可能影响历史。当前通过 JSON 序列化和反序列化复制简单数据，再保存到订单。

再次点餐会复制历史清单，恢复门店和取餐方式，并替换当前购物车。未来要提醒覆盖，并按当前商品目录重新校验价格和库存。JSON 复制适合这里的简单数据，不能说它可以无损复制函数、循环引用等任意对象。

### 28. 订单状态怎么管理？是实时的吗？

参考回答：本地定义制作中、待取餐、已完成三个状态，按固定顺序前进；完成后不再继续。页面通过当前状态计算进度、文案与列表分类。

它不是实时商家反馈。“刷新订单状态”实际调用 `advanceOrder` 推进本地状态；真实应用应由服务端状态驱动，客户端查询或订阅更新。当前没有待付款、取消、退款等完整交易状态。

### 29. 地图是真实地图吗？当前位置和距离怎么来的？

参考回答：H5 使用在线 OpenStreetMap 地图嵌入，非 H5 使用 uni-app 的 map 组件。默认中心是学院附近的预设坐标，切换餐厅会更新地图目标。真实地图底图与实时设备定位是两件事。

当前没有主动调用设备定位来更新默认中心，距离和出餐时间来自配置；非 H5 的 map 设置了 `show-location`，实际用户位置显示仍受平台能力和权限影响。没有实现路线导航和实时距离计算。H5 地图需要外网，不能说整个系统完全离线。

### 30. 图片与性能做了哪些优化？

参考回答：线上 25 道餐品各自使用独立图片，正式餐品和场景素材采用 WebP，并移除一批不再使用的旧素材。商品卡和详情页还提供图片失败时的文字降级，避免留下空白区域。

性能结果只能引用有记录的数据：2026-10-02 的小程序生产产物约 1.64 MiB，这是当时构建目录体量，不等同于任何平台的最终上传包指标。没有完成首屏耗时和帧率基准测试；也没有实现完整的图片懒加载、虚拟列表或分包优化。

### 31. 没有后端，为什么仍然有项目价值？

参考回答：当前交付集中体现移动端开发：页面与组件设计、规格交互、状态共享、价格计算、页面导航和本地持久化。它可以用于验证点餐交互和业务流程，但不能提供真实多用户服务。

如果老师明确要求后端或数据库，应承认当前交付还需要补充；不要把“课程一般不需要后端”当成事实。项目范围应以本课程评分要求为准。

### 32. 如果增加数据库，会怎么设计？

参考回答：这是后续设计。可以建立用户、餐厅、档口、商品、规格、订单、订单明细和用户优惠券等表。档口关联餐厅，商品关联档口，订单关联用户与餐厅，订单明细保存商品、规格和成交价快照。

追问多档口订单：可增加主订单和档口子订单，统一支付，按档口分别处理制作状态。库存扣减、优惠券使用和订单创建需要服务端保证一致性；这些目前还没有实现。

### 33. 本地数据安全吗？订单号会重复吗？

参考回答：本地缓存可被修改，当前用于展示，不适合作为真实金额、会员权益和订单状态的可信依据。真实系统应由服务端验证用户身份、商品价格、优惠和状态变化，不能相信前端传入的总价。

当前订单号取日期与部分时间戳，取餐码为三位随机数，没有全局唯一保证。线上应由服务端分配订单号，取餐码结合餐厅、日期或有效订单范围管理。客户端点击锁解决不了跨设备重复请求。

### 34. 项目的难点或亮点是什么？遇到什么问题？

参考回答：主要难点是让同一份业务数据在多个页面保持一致，并处理不同餐品的规格与计价。项目通过统一状态模块、配置化规格和订单快照实现这条流程。多端地图需要分别适配，图片资源也需要兼顾清晰度与移动端体积。

亮点可讲“校园多档口场景、完整本地交互、可重复演示和素材优化”。不要称为算法创新、智能推荐或高并发系统；首页推荐来自静态 `featured` 标记。

### 35. 项目还有什么不足？如果再做一周，优先改哪里？

参考回答：首先补齐客户端边界，例如规格组合键、优惠券有效性、再次点餐覆盖提醒和缓存异常处理；再完善餐厅、档口和商品的独立关系。之后根据课程范围接入登录、库存和服务端订单，最后做目标平台真机检查。

也可以指出辅助入口的不足：客服、开票和通知有些只是提示，会员积分能累积但没有完整自动升级逻辑。这样回答体现的是对现状有判断，不需要声称项目没有问题。

### 36. 项目是自己做的吗？用了 AI 或模板吗？你具体学到了什么？

参考回答框架：项目基于已有 uni-app 工程进行了重构，使用了 AI 辅助代码整理、界面和素材制作。本人实际完成或理解的部分应据实说明，例如需求确定、运行调试、业务流程核对和某个功能的修改。对于借助工具完成的部分，可以解释其作用、数据流和限制。

不要照背未经实际完成的个人贡献。准备一个能独立解释并修改的例子：改商品基础价、改优惠门槛、增加一个规格，指出改哪份配置、哪些计算属性会更新、需要补哪些验证。若学校要求披露工具使用，按课程要求说明。

## 三、老师临时要求现场改动时的练习题

这部分是排练题，不表示代码已经进行了这些修改。正式演示前恢复练习改动。

| 练习 | 从哪里入手 | 改完应检查什么 |
| --- | --- | --- |
| 把某餐品价格调高 1 元 | `catalog.js` 的 `priceCents` 增加 100 | 列表、详情及新加入购物车的价格；旧购物车是快照，不一定同步 |
| 新增一个餐品 | 在 `PRODUCTS` 增加唯一 id、有效 stallId、图片、价格、规格 | 对应档口数量、搜索、详情、加购；商品卡不要显示缺图 |
| 把优惠券改成满 40 减 6 | `thresholdCents` 改为 4000 | 39.60 元不可用，40 元可用；当前已选券需注意重新校验 |
| 搜索中加入新的匹配字段 | 点餐页 `filteredProducts` | 新字段命中、空关键词、无结果反馈 |
| 新增一种取餐方式 | 状态设置、结算选项、订单字段与显示 | 不能只加一个按钮；所有分支都要同步支持 |

遇到暂时不会的问题，可以说：“当前这一部分没有实现，我先说明现有流程；如果增加这个能力，我会从数据关系、页面状态和验证这几个位置修改。”随后说出具体位置，不要只说“调用接口就行”。
