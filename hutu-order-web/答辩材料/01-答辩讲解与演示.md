## 1. 项目定位与回答原则

本项目是使用 uni-app 与 Vue 3 开发的校园点餐移动端交互原型，围绕选择餐厅、浏览档口、选择餐品规格、购物车结算、订单查询构成完整的本地业务流程。当前主要验证环境为 H5，已具备微信小程序构建产物。

课程答辩应重点展示需求分析、页面组织、组件复用、响应式数据、页面通信、移动端适配，以及如何验证功能。页面美观是辅助，能够说清“点一个按钮后数据怎么变化”更重要。

参考稿中的第一人称表达，请结合自己的实际工作与理解使用。项目经过已有代码重构并使用了 AI 辅助；不要把借助工具完成的全部过程说成独立从零手写。准备时要能定位、解释和修改关键代码。

| 项目事实 | 答辩时的准确表述 |
| --- | --- |
| Vue 版本 | `package.json` 声明 Vue 3.4.21，页面主要使用组合式 API 与 `<script setup>` |

## 2. 约 5 分钟讲解稿

### 0:00—0:40　介绍题目与需求

老师好，我的课程设计题目是《基于 uni-app 与 Vue 3 的校园多档口点餐应用设计与实现》。项目以校园餐厅为场景，面向学生提供餐品浏览、规格选择和订单查询功能。

校园餐厅通常包含多个档口，不同档口又有不同种类的餐品。因此，项目围绕餐厅选择、档口分类和餐品详情组织界面，覆盖盖饭、粉面、河南风味、饺子馄饨、轻食烘焙和饮品六类内容。本次实现主要聚焦移动端界面与本地业务交互。

### 0:40—1:20　介绍技术与结构

技术上使用 uni-app 和 Vue 3。Vue 负责组件化与响应式界面，uni-app 提供页面管理、跨端基础组件和统一 API。项目使用 Vite 进行开发与构建，使用 SCSS 管理页面样式。

代码主要分为四部分：页面负责展示与交互，公共组件负责餐品卡片和空状态，数据模块定义餐厅和餐品目录，状态模块集中管理购物车、订单与收藏。数据变化通过 Vue 的响应式机制更新界面，并通过 uni-app 的本地存储 API 保存。

### 1:20—2:40　演示选餐与结算

现在演示一次完整点餐。首页提供门店信息和档口入口，进入点单后，可以按档口浏览，也可以输入关键词搜索。目前有六个档口，每个档口先列本档餐品，再按销量补上同店其他档口的推荐，一页共十道。

我先选择黑椒鸡腿饭。详情页可以选择份量和加料，这里保持标准份，加一个煎蛋。页面根据选择自动计算价格，加入购物车后再到河南风味档口选择一份河南烩面。

购物车统一显示两个档口的餐品，并保留各自的规格与档口名称。结算页可以设置取餐方式、时间、备注与优惠券。这次餐品金额是 39.60 元，使用满 30 减 6 元的校园券后是 33.60 元。金额在程序中使用整数“分”计算，到界面展示时才转换成“元”。

### 2:40—3:20　演示订单与持久化

确认后会生成本地订单，并进入订单详情页。这里展示取餐码、餐品清单、金额和订单进度。当前支付是模拟流程，不会产生真实扣款。为了演示订单生命周期，可以通过按钮把订单从制作中推进到待取餐，再到已完成。

历史订单支持查看详情和再次点餐。订单和购物车保存在本地，因此同一浏览器、同一站点重新打开后仍能恢复。切换餐厅时，如果购物车有餐品，会先提示确认并清空，避免把不同餐厅的购物车混在一起。

### 3:20—4:20　解释关键实现

我重点讲三个实现。第一是状态共享：各页面调用同一个状态模块，购物车数量、合计和当前餐厅都从统一数据源获得，因此无需在多个页面重复维护。

第二是规格和购物车。每道餐品的规格由数据配置决定，详情页统一渲染单选或多选选项。购物车根据餐品编号与已选规格组合区分条目，同一组合再次加入会增加数量。创建订单时会复制当前购物车数据，保存下单时的名称、价格和规格，避免以后修改购物车影响历史订单。

第三是多端适配。界面主要使用 uni-app 基础组件，布局使用 rpx、Flex 和安全区间距。地图通过条件编译区分 H5 和非 H5 实现，保留业务逻辑复用，同时处理平台差异。

### 4:20—5:00　验证、限制与收获

验证方面，项目此前完成了 H5 交互检查以及 H5、微信小程序生产构建检查；还检查了每个档口的餐品数量与图片完整性。现场演示主要展示选餐、结算、订单状态和数据恢复。

当前版本没有后端、真实登录、库存扣减和支付接入，餐厅也共用餐品目录。下一步可以增加餐厅与档口的独立数据关系，通过服务端管理库存、订单和支付状态。

通过这个项目，我主要学习了如何用 Vue 的响应式和组件化组织移动端页面，以及如何在 uni-app 中处理页面跳转、本地存储和平台差异。我的讲解到这里，谢谢老师。

## 3. 可重复的现场演示脚本

正式演示前可在“我的 → 设置 → 恢复默认设置”恢复初始数据。该操作会覆盖当前本地订单、购物车和偏好，先确认没有需要保留的演示记录。初始状态已有 2 个样例订单、2 张券、860 积分，不是空白账户。

| 步骤 | 操作 | 应看到的结果 | 对应讲解点 |
| --- | --- | --- | --- |
| 1 | 首页进入点单 | 默认餐厅、档口列表 | 页面结构和导航 |
| 2 | 现炒盖饭 → 黑椒鸡腿饭 | 基础价 ¥18.80 | 数据驱动商品详情 |
| 3 | 标准份，加煎蛋，数量 1，加入购物车 | 单价 ¥20.80 | 规格附加价、计算属性 |
| 4 | 返回点单 → 河南风味 → 河南烩面 | 标准份，保持默认辣度，不加料，数量 1 | 不同档口共用详情模板 |
| 5 | 加入购物车，再打开购物车 | 2 件，总计 ¥39.60 | 跨档口汇总、档口归属 |
| 6 | 去结算 → 农大校园券 | 满 ¥30 减 ¥6，实付 ¥33.60 | 门槛校验、整数金额 |
| 7 | 输入备注，确认支付一次 | 创建新订单，购物车清空 | 提交防连点、本地模拟支付 |
| 8 | 连续两次“刷新订单状态” | 制作中 → 待取餐 → 已完成 | 有限状态流转 |
| 9 | 我的 → 全部订单 | 初始 2 单加新单，共 3 单 | 订单列表与状态共享 |
| 10 | 浏览器刷新后查看刚创建的订单 | 订单保留 | 本地持久化 |
| 11 | 可选：已完成订单 → 再来一单 | 恢复餐品与原规格到购物车 | 订单快照复用 |

上述场景使用初始数据时，提交后积分为 893，剩余优惠券为 1 张。再次演示前若未恢复初始状态，券数、订单数和积分可能不同。取餐码随机生成，不背固定号码。

说明地图时说“默认展示学院附近”，不要说“刚刚通过 GPS 获取到了我的位置”。地图需要网络；点餐数据与订单不需要业务后端。浏览器展示的是 H5 移动视口，不等于微信小程序真机。

## 6. 当前边界与补充说明

这些是准备追问时要知道的真实情况，不需要在开场逐项展开。

- 没有用户认证与数据库。会员身份是预置数据，本地存储可被用户修改，不能承担线上交易信任依据。
- 餐品通过 `stallId` 对应档口，订单记录 `storeId`；当前没有把档口按 `storeId` 分配给不同餐厅，也没有按档口拆单和分别出餐。
- 支付方式选择目前只是页面选中状态，没有渠道调用，也没有写入订单支付记录；650 毫秒延时只是模拟等待。
- 优惠券页面筛选持有状态和金额门槛；创建订单复核金额门槛，但没有完整复核持有状态和有效期。不要称为完善的优惠券核销系统。
- “刷新订单状态”是本地手动推进。没有服务端轮询、WebSocket 或商家接单系统。
- `reorder` 会用历史清单替换当前购物车，沿用旧价格；没有新价格、售罄、库存校验。
- 订单号基于日期和时间戳的一部分，取餐码为三位随机数；没有服务端唯一性保证。
- 地图中心、餐厅距离、营业信息为配置。部分地点名称和门店展示图用于场景演示，不代表已经接入真实商家的实时数据；商品图包含生成素材，不是现场实拍证明。
- 开票、客服、通知等部分辅助入口仅提供提示；会员积分会增加，但等级没有自动升级规则。
- 本地存储使用版本化键隔离旧数据，不等于完成数据库迁移；当前没有完整缓存结构校验、异常恢复机制。
- 当前代码仍有可整理的遗留资源与样式，不能把“全部冗余清零”作为已经证明的成果。

如果课程评分表明确要求后端、真实登录、数据库、App 安装包或小程序真机运行，需要补足对应交付；仅凭“要求 uni-app 和 Vue”无法推定这些也已经满足。
